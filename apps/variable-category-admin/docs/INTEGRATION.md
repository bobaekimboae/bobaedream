# 기존 중고차 매물 관리자 통합 실행서

## 결론

기존 관리자와 신규 관리자를 DB JOIN으로 합치지 않는다. 기존 관리자는 매물 원장을 유지하고 신규 관리자는 분류·스키마·노출 정책을 제공한다. 연결점은 `ListingGateway` 하나로 제한한다.

## 통합 단계

### 1. 실제 구조 조사

- 운영 중인 Laravel/PHP 버전과 배포 방식을 기록한다.
- 매물 테이블, PK 형식, 상태 코드, 카테고리 코드, 판매자 유형을 확인한다.
- 읽기·쓰기 경로, 캐시, 검색엔진, 배치, 장애 복구 책임자를 기록한다.
- 결과는 `docs/adr/001-platform-integration.md`의 결정란에 승인받는다.

### 2. 읽기 전용 연결

- 기존 DB에 전용 읽기 계정을 만든다.
- `config/listing-contract.php`에 컬럼 매핑을 설정한다.
- 운영 비밀값은 GitHub Actions Environment 또는 Secret Manager에만 저장한다.
- 어댑터는 원본 컬럼명을 도메인 밖으로 노출하지 않는다.

### 3. 코드 매핑

`external_code_mappings`에 다음을 버전별로 등록한다.

- 기존 카테고리 → `VEHICLE_TYPE`
- 기존 카테고리 → `category_node.system_key`
- 기존 판매자 코드 → `seller_type`
- 제조사·모델 코드 → 표준 코드

매핑되지 않은 값은 실패로 기록하고 운영 검수 큐에서 처리한다.

### 4. Shadow Read

신규 Resolver를 사용자 응답에 반영하지 않고 병렬 실행한다. 유형·카테고리·필터·Placement별 일치율, 미매핑률, 지연시간을 집계한다.

권장 통과 기준:

- 핵심 중고차 유형 일치율 99.9% 이상
- 미매핑 0.1% 이하이고 전건 검수 큐 적재
- p95 추가 지연 50ms 이하
- 오류 발생 시 기존 결과로 즉시 복귀

### 5. 신규 등록 연결

1. 차량유형과 카테고리 선택
2. Published 등록 스키마 조회
3. 공통 필드는 기존 매물 컬럼에 저장
4. 확장 필드는 `listing_attribute_values`에 저장
5. 저장 성공 후 Outbox Event 발행
6. Resolver와 검색 인덱스 갱신

동일 DB라면 한 트랜잭션과 Outbox를 사용한다. 별도 DB라면 분산 트랜잭션을 만들지 않고 멱등 이벤트와 재처리를 사용한다.

### 6. 단계적 전환

- 내부 운영자 5%
- 신규 등록 5%
- 신규 등록 25%
- 신규 등록 100%
- 기존 매물 검색·상세
- 최종 전체 노출

각 단계는 오류율, 미매핑률, 검색 0건 비율, 등록 이탈률과 rollback rehearsal을 확인한 뒤 승격한다.

## 금지

- 기존 매물 테이블 전체 복제
- 운영 `listings_stub`
- 기존 DB에 신규 관리자의 임의 FK 추가
- 신규 관리자의 직접 상태 변경
- 알 수 없는 코드를 CAR로 강제 매핑
- API 성공 전에 양쪽 DB에 순차 dual write
