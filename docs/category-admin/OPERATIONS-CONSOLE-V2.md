# 보배드림 차량유형 운영 관리자 V2 개발 지시문

문서 상태: 개발 정본 2차안  
적용 브랜치: `codex/category-admin-operations-console`  
적용 코드: `admin-server/`, `public/category-admin/`, `apps/variable-category-admin/`  
목표: 보배드림 개발팀이 실제 운영망 연동을 시작할 수 있는 다중 차량유형 Control Plane

## 1. 제품 목표

현재 중고차 단일 유형 관리자에 화면과 필드를 계속 추가하는 방식은 중단한다. 기존 중고차 관리자는 매물·판매자·가격·사진·심사·거래상태의 정본(Data Plane)으로 유지하고, 신규 관리자는 차량유형별 카테고리·가변 필드·화면 스키마·판매자 정책·배포 버전을 관리하는 설정 정본(Control Plane)으로 둔다.

관리자는 코드 배포 없이 다음 항목을 차량유형별로 바꿀 수 있어야 한다.

- 검색 필터와 표시 순서
- 매물 등록폼의 필수·권장·선택 입력
- 매물 목록 카드의 핵심 정보와 표시 순서
- 상세보기 정보 섹션과 표시 순서
- 옵션 그룹과 카테고리 뎁스
- 판매자 유형별 등록 권한과 검증 정책
- PC웹·모바일웹·모바일앱별 노출 규칙
- 다중 카테고리 노출 규칙
- Draft·검수·승인·배포·롤백

## 2. 운영 화면 설계 원칙

공개된 대형 자동차 플랫폼 관리자에서 공통적으로 확인되는 운영 패턴을 보배드림 목적에 맞게 재구성한다.

| 참고 패턴 | 보배드림 적용 |
|---|---|
| AutoScout24식 재고·품질 KPI | 누락 필드, 미검수 스키마, 배포 실패, 매핑 실패를 대시보드의 작업 항목으로 노출 |
| Auto Trader식 문의·리드 상태 | 판매자 채널과 리드 정책은 차량유형과 분리하고 운영 현황에서 별도 집계 |
| vAuto·LotPilot식 작업 대기열 | `수정 필요 → 검수 대기 → 승인 대기 → 배포 가능` 순으로 다음 행동을 명확히 표시 |
| Cars Portal식 운영자·딜러 분리 | 플랫폼 Super Admin, 카테고리 운영자, QA, 배포자, 딜러 관리자 권한을 분리 |
| mobile.de식 누락 경고 | 등록폼 필수값, 리스트 메타, 출처 URL, 한국 적용 판단 누락을 배포 차단 오류로 처리 |

한 사이트의 화면을 복제하지 않는다. 정보 구조와 업무 흐름만 참고하고 보배드림 카테고리 구조와 운영 용어로 통일한다.

## 3. 사용자와 권한

| 역할 | 주 업무 | 제한 |
|---|---|---|
| `SUPER_ADMIN` | 전체 설정·권한·긴급 롤백 | 운영 계정 최소화 |
| `PRODUCT_OWNER` | 정책 결정·작성·검수 요청 | QA 승인·배포 불가 |
| `CATEGORY_MANAGER` | 카테고리·필드·스키마 작성 | QA 승인·배포 불가 |
| `QA_REVIEWER` | 화면·데이터·규칙 검수 | 원본 설정 직접 수정 불가 |
| `PUBLISHER` | 승인된 Release 배포·롤백 | Draft 수정 불가 |
| `READ_ONLY` | 조회·감사·비교 | 쓰기 불가 |

딜러·상사·브랜드 인증 사업자는 플랫폼 운영자와 같은 관리자 화면을 사용하지 않는다. 향후 별도 Dealer Console에서 자기 재고·리드·상품만 관리한다.

## 5. 차량유형과 자산유형 정본

### 5.1 VEHICLE_TYPE

- `CAR` — 중고차 / Used Cars
- `BIKE` — 바이크 / Motorcycles
- `TRUCK_SPECIAL` — 트럭·특장차 / Trucks & Special Vehicles
- `BUS` — 버스 / Buses
- `CAMPING_CARAVAN` — 캠핑카·카라반 / Motorhomes & Caravans
- `CONSTRUCTION` — 건설기계 / Construction Equipment
- `MATERIAL_HANDLING` — 자재운반장비 / Material Handling Equipment

`FORKLIFT`는 독립 차량유형이 아니라 `MATERIAL_HANDLING`의 하위 카테고리다. 지게차 매물의 원본 유형은 `MATERIAL_HANDLING` 하나만 갖고 건설기계·자재운반장비·지게차 메뉴에 동시에 배치할 수 있다.

### 5.2 ASSET_TYPE

- `ATTACHMENT` — 어태치먼트 / Attachments
- `PARTS_GOODS` — 부품·용품 / Parts & Accessories

어태치먼트는 건설기계 하위와 부품·용품 양쪽에 노출할 수 있다. 차량 본체와 같은 등록폼·검색 Projection을 사용하지 않는다.

### 5.3 카테고리·Overlay·판매자 채널

아래 항목은 VEHICLE_TYPE으로 만들지 않는다.

- 수입차: `IMPORT_OVERLAY`
- 전기차: `EV_OVERLAY`
- 브랜드인증 중고차: 인증 Overlay + 판매자 채널
- 매매단지별 중고차: `DEALER_COMPLEX` 판매자 채널
- 리스중고차: `LEASE_TAKEOVER` 거래방식
- 럭셔리카·슈퍼카·클래식카·튜닝카: Theme Overlay
- 개인·딜러·상사·업체: Seller Channel
- 상단노출·프리미엄·리드상품: Service/BM

## 8. 화면 스키마 편집 규칙

각 스키마 항목은 다음 속성을 가져야 한다.

- 표시 순서
- 한국어 화면명
- 내부 `item_key`
- 데이터 타입과 단위
- UI 컴포넌트
- 필수·권장·선택·시스템·조건부
- 기본 노출·더보기·조건부·숨김
- PC웹·모바일웹·모바일앱 노출 여부
- 조건식
- 검증 규칙
- 값 집합 또는 마스터 참조
- 기존 필드 매핑
- 설계 근거 URL
- 한국 적용 판단
- 변경 사유

Published 스키마는 직접 수정하지 않는다. 복제한 Draft에서만 수정한다.

## 9. 화면 미리보기와 QA

스키마 편집 화면에서 다음 미리보기를 제공한다.

- PC웹 검색 필터
- 모바일 바텀시트 필터
- PC웹 매물 목록 카드
- 모바일 매물 목록 카드
- 매물 상세 기본정보
- 등록폼

미리보기는 JSON 출력으로 끝내지 않는다. 실제 순서와 라벨, 필수 표시, UI 컴포넌트, 숨김·조건부 동작을 확인할 수 있어야 한다.

배포 전 QA는 다음을 확인한다.

1. 화면에 실제 노출되는가
2. 입력값이 API와 DB에 저장되는가
3. 기존 필드 매핑이 손실 없이 동작하는가
4. 검색 Projection에 반영되는가
5. 목록·상세 표시 순서가 스키마와 일치하는가
6. 권한 없는 사용자가 수정·승인·배포하지 못하는가
7. 이전 Published 버전으로 롤백 가능한가

## 10. 운영 대시보드

대시보드는 수치 나열보다 행동 우선으로 설계한다.

### 첫 화면 필수 영역

- 배포 차단 오류
- 검수 대기 스키마
- QA 승인 대기
- 배포 가능한 Release
- 매핑 실패 매물
- 출처·한국 적용 판단 누락
- 최근 배포와 롤백 가능 버전
- 차량유형별 완성도

각 카드에는 `문제 수`, `영향 범위`, `마지막 변경자`, `다음 행동`을 표시한다.

## 11. UI 시스템

- 데스크톱 운영 화면을 우선하되 1024px까지 정상 사용 가능해야 한다.
- 좌측 내비게이션은 업무 도메인별 그룹으로 나눈다.
- 상단에는 환경, API 연결상태, 사용자 역할, 전역 검색을 둔다.
- 본문 기본 글자 14~16px, 핵심 상태·액션은 색상과 텍스트를 함께 사용한다.
- 표는 고정 헤더, 행 선택, 검색, 필터, 정렬, 페이지네이션을 지원한다.
- 편집은 우측 Drawer 또는 전용 상세 화면을 사용하고 작은 모달에 복잡한 폼을 넣지 않는다.
- 위험 작업은 영향 범위와 롤백 대상을 확인한 뒤 실행한다.
- 상태 색상만으로 의미를 전달하지 않는다.
- 로딩, 빈 화면, 오류, 권한 부족, 충돌, 저장 성공 상태를 모두 제공한다.

보배드림 운영 콘솔의 시각 방향은 짙은 남색 내비게이션, 밝은 작업 캔버스, 파란 주요 액션, 절제된 상태 색상을 사용한다. 자동차 소비자 화면의 카드 스타일을 관리자에 그대로 옮기지 않는다.

## 12. API 추가 범위

```http
GET  /api/admin/variable-matrix
GET  /api/admin/variable-matrix/{scope_key}
GET  /api/admin/work-queue
GET  /api/admin/schema-preview/{schema_id}
POST /api/admin/schemas/{schema_id}/validate
POST /api/admin/releases/{release_id}/dry-run
POST /api/admin/releases/{release_id}/publish
POST /api/admin/releases/{release_id}/rollback
```

공개 API는 Published resolved snapshot만 반환하고 Draft 원본 테이블을 직접 노출하지 않는다. ETag는 `schema_hash`를 사용한다.

## 14. 완료 판정

다음 조건을 모두 만족해야 실서버 연동 준비 완료로 판정한다.

- 10개 유형·자산의 필터, 등록폼, 목록, 상세 스키마가 존재한다.
- 각 유형의 실제 필드와 표시 순서를 관리자에서 확인할 수 있다.
- Draft와 Published가 물리적·논리적으로 분리된다.
- 권한, 감사 로그, 승인, 배포, 롤백 테스트가 통과한다.
- 공개 API는 Published snapshot만 반환한다.
- 기존 매물 원본을 복제하지 않고 Adapter 계약으로 연결한다.
- 매핑 실패는 조용히 CAR로 폴백하지 않고 격리한다.
- 부품·용품과 어태치먼트는 차량 본체 등록 구조와 분리된다.
- PC웹·모바일웹·모바일앱 미리보기와 QA 체크리스트가 제공된다.
- Docker, CI, migration rehearsal, 보안 검사가 통과한다.

## 15. 이번 브랜치의 1차 완료 범위

이번 브랜치에서는 다음까지 완료한다.

1. 운영 콘솔 UI 셸
2. 전체 유형 레지스트리 보정
3. 차량유형별 가변 매트릭스 조회
4. 유형별 실제 필드 시드 확장
5. 스키마 화면 미리보기
6. 관련 API·테스트·문서

복잡한 Drag & Drop 편집, 운영 SSO, 실제 기존 DB 연결, 메시지 브로커 연결은 다음 단계로 분리하되 빈 API나 동작하지 않는 버튼은 배포하지 않는다.
